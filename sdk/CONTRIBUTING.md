# Contributing to Ameba SDK

Thank you for helping improve the TypeScript and Rust futures SDK. The
supported public boundary is described in [README.md](./README.md).
Participation is governed by the [Code of Conduct](./CODE_OF_CONDUCT.md).

## Before opening a change

- Use Node.js 22 or 24 and npm 10.9.8, matching `packageManager`.
- Do not commit credentials, wallet material, private endpoints, `.env` files,
  npm tokens, generated tarballs, or machine-specific paths.
- Open an issue before a large API redesign, a new runtime dependency, or an
  incompatible runtime requirement.
- The futures programs and their client crate own the wire format. The SDK
  mirrors it; it never redefines it. A layout or instruction change starts in
  the futures repository's `docs/interfaces.md`.

## Set up and validate

```bash
npm ci
npm run check
```

`npm run check` runs the typecheck, the TypeScript tests and the Rust tests.

## Golden vectors

`test/fixtures/futures/*.json` are generated by `tools/futures-vectors`, a Rust
program that links the futures crates from the monorepo's `../futures` and the
oracle interface from `../oracle`:

```bash
FUTURES_COMMIT=$(git log -1 --format=%H -- ../futures) npm run vectors
```

When the futures program changes, regenerate the vectors, then update the
TypeScript module until `npm test` passes. The Rust crate links
`ameba-futures-client` by path, so it always builds against the same tree.

## Public API changes

A public API change should include:

- exported TypeScript types with no implicit `any`;
- range validation for every value written to the wire;
- tests, ideally against Rust-generated vectors;
- updates to [docs/FUTURES.md](./docs/FUTURES.md) when developer behavior
  changes; and
- a changelog entry.
